  It has six sections:
  1. What the app must do, in priority order: token setup, Home with balances,
     Claim with tracking, unit tests, then Activity if there's time. The amount
     checks follow the API's rules: number format, maximum decimals, minimum
     amount, available balance, and what's left after the fee must be above
     zero.
  2. Other requirements:
     - Amounts are never handled as floating-point numbers.
     - Every API error the docs list is handled, including waiting after a "too
       many requests" error.
     - Claims carry an idempotency key, so a retry can't create a second claim.
     - The API base URL lives in one place, and the token is kept safe.
     - The app is built for the web at phone width, with frequent commits.
  3. The three decisions you have to explain, with options:
     - Amounts: use exact whole-number units for the maths.
     - Balance after a claim: three options are compared. I lean toward showing
       an "in progress" marker without faking the balance.
     - Unknown claim result: resend the same request with the same key, and save
       the attempt so a page reload can't cause a duplicate claim.

     The plan also notes that the brief wants you to ask an AI for at least two
     approaches to the balance decision.
  4. A 2-hour schedule (14:00–16:00 UTC): commit points, deploying as soon as
     Home works, and a suggested file layout.
  5. A checklist of everything to submit.
  6. Assumptions to copy into NOTES.md: "Max" means the full available amount,
     and the fee is a flat amount per asset.

  I left your token out of the file on purpose, since the repo will be public.

     Fix the Activity screen: no scroll, no Back button

     Context

     You reported that Activity can't scroll and the Back button is missing. The
     cause is in App.tsx ActivityScreen (around line 262). Every other screen
     uses Page, which is a ScrollView. Activity instead uses a plain <View 
     style={s.page}> that wraps a FlatList.

     s.page only has flexGrow: 1. Without a height limit, the View grows to the
     full height of the list, so the FlatList has nothing to scroll inside. The
     Expo web page also turns off scrolling on the page itself (body { overflow:
     hidden }), so nothing scrolls at all.

     That causes a second problem: the end of the list is always "in view", so
     onEndReached keeps firing and loads every page in a row. The result is a
     very tall, broken layout, and that is most likely why Back ends up out of
     reach.

     Fix (App.tsx only)

     1. Give the Activity container a fixed height: style={[s.page, { flex: 1, 
        minHeight: 0 }]}, so it fills the viewport and stops there.
     2. Give the FlatList style={{ flex: 1 }}, so it becomes the only part that
        scrolls.
     3. Keep the <Back> and the "Activity" title above the list, inside the
        fixed container. They then stay visible while the list scrolls; nothing
        else to change there.
     4. Add a guard to onEndReached so it doesn't run while the first page is
        still loading or after an error. more() already returns early on loading
        and cursor === null; also skip when error != null, so a failed request
        doesn't retry in a loop. The "Retry" button in the list footer stays the

       the screenshot.
