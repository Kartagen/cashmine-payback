     Design refresh + Expo Router

     Context

     The current UI in App.tsx is a generic blue/card style: tinted banners,
     pill chips, blue links, ‹ Back text and a ✕ glyph. You want a calm,
     editorial look (Things 3 / Linear mobile) defined by written design rules,
     and you chose to move to Expo Router so the app gets a real stack, large
     titles and browser back. The work has three parts: (1) write the rules into
     app/CLAUDE.md, (2) add src/theme.ts as the single source of colors and
     type, (3) split App.tsx into routes and restyle them. Business logic stays
     as it is: src/api.ts, src/amount.ts, src/claims.ts.

     1. app/CLAUDE.md

     After @AGENTS.md, add the ## Design rules block exactly as you wrote it,
     plus two lines that come from your answers:
     - Söhne isn't bundled because it's a paid license. The font stack is Söhne 
       → Inter (bundled) → system-ui.
     - Errors may use a single danger red (theme.color.danger), for error text
       only. It is not an accent.

     2. Dependencies (npx expo install …)

     - expo-router react-native-safe-area-context react-native-screens 
       expo-linking expo-constants: needed by the router.
     - expo-font @expo-google-fonts/inter: Inter 400/500/600.
     - phosphor-react-native react-native-svg: icons.

     Config:
     - package.json: "main": "expo-router/entry".
     - app.json: scheme: "cashmine", plugins: ["expo-router"], web.output: 
       "single".
     - Delete App.tsx and index.ts.
     - public/vercel.json: add an SPA rewrite { "source": "/(.*)", 
       "destination": "/index.html" } so /activity and /claim/BTC survive a
       reload. Keep the existing CSP. font-src 'self' already covers bundled
       fonts.

     3. src/theme.ts (new, the only place hex values live)

     - color: text #1A1A1A, bg #FAF8F5, accent #D9480F, secondary #6B6862 (warm
       gray for meta text), hairline rgba(26,26,26,0.12), danger #B42318.
     - hairline = StyleSheet.hairlineWidth, and spacing 4/8/12/16/24/32.
     - type scale. Each entry sets fontSize, lineHeight and fontFamily:
       - largeTitle 34/41 600
       - title 20/25 600
       - body 16/22 400
       - bodyStrong 16/22 500
       - footnote 13/18 400
       - figure 34/41 600 tabular
     - num = { fontVariant: ['tabular-nums'] } for every amount, date and fee.
     - fontFamily comes from Platform.select: on web, 'Söhne, Inter_400Regular, 
       system-ui, sans-serif' (one per weight); on native, Inter_400Regular and
       so on.

         more, Retry, Check now).

       - The blue color is removed everywhere.
     - Asset selector: a plain row of text tabs. The selected one gets text
       color plus a 2px text-colored underline; the others are secondary.
     - Destinations: a hairline list with Phosphor RadioButton/Circle icons.
     - Inputs: transparent with a hairline border, radius 8, body + num.
     - Errors: danger footnote text plus a secondary Retry button. The pink box
       is removed.

       icons.

⏺ I found one real bug that I reproduced, plus five smaller ones from reading
  the code; I've changed nothing yet. Everything below is from reading all
  ~1,000 lines and running browser tests against a mocked API.

  The real bug

  1. The confirm step can go blank and trap you (src/app/claim/[asset].tsx:103).
     The confirm content only shows while the amount still passes validation,
     and validation re-runs against the live balance, which refreshes every 15
     s. If your available balance drops below the amount while you're reviewing
     (a reversal, or a claim from another device), Confirm and Edit both
     disappear. I reproduced it: the screen shows only the "Confirm claim"
     title, and the only way out is Back. Fix: keep the review open, and when
     the amount is no longer valid, show the error and the Edit button instead
     of nothing.

  Smaller bugs, not reproduced

  2. Timeout doesn't cover reading the response (src/api.ts:65). The 15 s timer
     is cleared once headers arrive, so a response that stalls mid-body hangs
     forever. For a claim submit, that key then stays marked as in flight, and
     the status shows "Sending claim…" until a page reload.
  3. A Retry-After date makes retries fire immediately (src/api.ts:70). The code
     only handles Retry-After in seconds. A date value (also allowed by the
     HTTP spec) becomes NaN, so rate-limited requests retry three times with no
     wait. Fix: fall back to 1 s when the value isn't a number.
  4. The token hint is missing when a refresh fails (src/app/index.tsx:28). If
     balances were already loaded and a refresh gets a 401, Balance shows the
     raw server message instead of "Your token is invalid or expired…". It's a
     one-word fix: use errText.
  5. An old failed request can show an error over fresh data (src/store.tsx:15).
     Polls can overlap. If an older request fails after a newer one succeeded,
     "Could not refresh" appears even though the numbers are current. loading
     can also flip to false while a request is still running.
  6. Confirm can show stale fees (src/app/claim/[asset].tsx:31). With the new
     options cache, a fee or minimum can be a few minutes old until the
     background refresh lands. The server re-checks on submit, so it can't cause
     a wrong claim, but the screen can briefly show an old value.

  Checked and fine: the money and idempotency logic holds up. Exact amounts are
  kept, the same idempotency key is reused on every resend, the failed-claim and
  "may have gone through" messages are right, double-tap is blocked, and the
  balance correction for new claims switches itself off. Dismissing a banner
  closes it without opening the claim status, and Activity no longer loads its
  first page twice.

  Should I fix 1–4? They're small and I'd test them the same way. I'd leave 5
  and 6 as known issues in NOTES.md, since they're rare and the server re-checks
  every claim on submit.

     claims.ts puts this logic inside a React hook, so plain Node can't run it.
     I'd move two pure functions out to the top of claims.ts (same file, no

       they are.

       uncertain: true } or { error }.

     - A failed claim says the money is back in the available balance.
     - unresolved is true for sending, unknown and pending, and false for
       completed, failed and errored.
